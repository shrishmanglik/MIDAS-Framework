# Cache Strategy Reference -- Astrology Calculations

## Overview

Astrology calculations and interpretations are highly cacheable because the same planetary configurations produce the same interpretations. A feature-hash caching strategy allows the first user to pay the AI interpretation cost while all subsequent users with similar chart features get instant, free results.

**Cost model**:
- First unique chart configuration: ~$0.003 (Tier 2 light AI for interpretation)
- All subsequent matches: ~$0.00 (cache hit, no AI call)
- Projected cache hit rate at scale: 85-95% for common yoga/dasha interpretations

---

## What to Cache

### Layer 1: Planetary Position Cache (Short-lived)

**What**: Raw planetary longitudes for a given Julian Day Number.

**Why**: The same birth moment always produces the same planetary positions. Swiss Ephemeris calls are CPU-intensive but deterministic.

**Key formula**:
```
cache_key = "ephemeris:" + sha256(
    julian_day_number_rounded_to_6_decimals +
    "|" + ayanamsa_type
)
```

**Value stored**:
```json
{
  "planets": {
    "sun": { "tropical": 354.6234, "sidereal": 330.8967 },
    "moon": { "tropical": 69.3412, "sidereal": 45.6145 },
    ...
  },
  "ayanamsa_degrees": 23.7267,
  "computed_at": "2024-01-15T10:00:00Z"
}
```

**TTL**: 24 hours. Planetary positions for a historical date never change, but ephemeris precision may improve with Swiss Ephemeris updates. For current transits, 24-hour TTL ensures daily positions stay fresh.

**Storage**: Redis or in-memory LRU cache (positions are small, ~2KB per entry).

---

### Layer 2: Chart Feature Cache (Medium-lived)

**What**: Computed chart features -- house placements, dignities, yogas detected, dasha periods -- derived from planetary positions.

**Why**: The same planetary positions always produce the same chart features. This layer avoids re-running the classification logic.

**Key formula**:
```
cache_key = "chart:" + sha256(
    ascendant_sign + "|" +
    house_system + "|" +
    sorted_planet_positions_rounded_to_degree.join("|")
)
```

**Rounding strategy**: Round each planetary sidereal longitude to the nearest whole degree for the cache key. This means charts within ~30 arcminutes of each other share the same cache key. This is acceptable because:
- House placements only change at sign boundaries (30-degree intervals)
- Yoga rules are sign-based, not degree-based
- Nakshatra boundaries are 13.33 degrees apart
- A 1-degree rounding captures all structurally identical charts

**Value stored**:
```json
{
  "ascendant": { "sign": "Simha", "nakshatra": "Magha" },
  "planet_placements": [
    { "planet": "Sun", "sign": "Meena", "house": 8, "dignity": "neutral", "nakshatra": "PBhadra" },
    ...
  ],
  "yogas_detected": ["Gajakesari", "Budhaditya"],
  "dasha_at_current_date": { "mahadasha": "Jupiter", "bhukti": "Saturn" },
  "computed_at": "2024-01-15T10:00:00Z"
}
```

**TTL**: 7 days. Chart features for a natal chart never change, but the "dasha_at_current_date" field needs periodic refresh. Natal-only features could be cached indefinitely.

**Storage**: Redis with JSON serialization (~5KB per entry).

---

### Layer 3: Interpretation Cache (Long-lived)

**What**: Human-readable interpretation text generated by the AI model for a specific combination of chart features.

**Why**: This is the expensive layer -- each AI interpretation costs $0.001-$0.10 depending on complexity. Identical chart feature combinations should produce the same interpretation.

**Key formula**:
```
cache_key = "interp:" + sha256(
    interpretation_type + "|" +
    ascendant_sign + "|" +
    sorted_yoga_identifiers.join(",") + "|" +
    sorted_planet_house_placements.join(",") + "|" +
    dasha_lord + "|" +
    detail_level
)
```

**Example cache key construction**:
```
interpretation_type = "natal_full"
ascendant_sign = "Simha"
yoga_identifiers = "Budhaditya,Gajakesari,SasaYoga"
planet_placements = "Ju-11,Ke-1,Ma-7,Me-8,Mo-10,Ra-7,Sa-6,Su-8,Ve-9"
dasha_lord = "Jupiter"
detail_level = "detailed"

raw_string = "natal_full|Simha|Budhaditya,Gajakesari,SasaYoga|Ju-11,Ke-1,Ma-7,Me-8,Mo-10,Ra-7,Sa-6,Su-8,Ve-9|Jupiter|detailed"
cache_key = "interp:" + sha256(raw_string)
```

**Value stored**:
```json
{
  "interpretation": {
    "sections": [...],
    "yogas_found": [...],
    "disclaimer": "...",
    "word_count": 1250
  },
  "generation_model": "tier2-light",
  "generation_cost_usd": 0.003,
  "generated_at": "2024-01-15T10:30:00Z",
  "hit_count": 0
}
```

**TTL**: Indefinite (no expiry). Natal chart interpretations do not change. The only reason to invalidate would be a significant improvement in interpretation quality (model upgrade), in which case a manual cache flush for the interpretation layer is appropriate.

**Storage**: PostgreSQL (for persistence and queryability) with Redis as a read-through cache (~10-50KB per entry depending on detail level).

## Cache Key Design Principles

### 1. Deterministic Ordering

Always sort planet placements and yoga identifiers alphabetically before hashing. This ensures that two charts with the same features but computed in different orders produce the same cache key.

```python
def build_cache_key(chart_features, interp_type, detail_level):
    planets_sorted = sorted([
        f"{p['planet'][:2]}-{p['house']}"
        for p in chart_features['planet_placements']
    ])
    yogas_sorted = sorted(chart_features['yogas_detected'])

    raw = "|".join([
        interp_type,
        chart_features['ascendant']['sign'],
        ",".join(yogas_sorted),
        ",".join(planets_sorted),
        chart_features.get('dasha_at_current_date', {}).get('mahadasha', 'none'),
        detail_level
    ])
    return "interp:" + hashlib.sha256(raw.encode()).hexdigest()
```

### 2. Granularity Tradeoffs

| Approach | Cache Hit Rate | Accuracy |
|----------|---------------|----------|
| Exact degree positions | ~2% hits | Perfect accuracy |
| Rounded to 1 degree | ~15% hits | Near-perfect (same signs/houses) |
| Sign-level only | ~60% hits | Good (misses degree-specific nuances) |
| Yoga combo only | ~85% hits | Moderate (ignores non-yoga factors) |

**Recommended**: Use sign-level rounding for the cache key but store exact positions in the cached value. This balances hit rate with accuracy.

### 3. Namespace Separation

Prefix all cache keys with a namespace to avoid collisions:
- `ephemeris:` -- raw planetary positions
- `chart:` -- computed chart features
- `interp:` -- AI-generated interpretations
- `transit:` -- daily transit data (shared across all users)

## Cache Warming Strategy

### Daily Transit Cache

Pre-compute and cache planetary positions for the current day at midnight UTC. All users checking "today's transits" hit the same cache.

```
transit_cache_key = "transit:" + date_string  // e.g., "transit:2024-01-15"
```

**TTL**: 25 hours (ensures overlap for timezone differences).

### Popular Configuration Pre-computation

Track the most common Ascendant + Moon sign combinations and pre-generate interpretations for them during off-peak hours.

## Cache Invalidation Rules

| Trigger | Action | Scope |
|---------|--------|-------|
| Swiss Ephemeris version update | Flush Layer 1 (ephemeris) | All entries |
| Interpretation model upgrade | Flush Layer 3 (interpretation) | All entries |
| Bug fix in yoga detection | Flush Layer 2 (chart) and Layer 3 | All entries |
| User reports incorrect interpretation | Invalidate specific cache key | Single entry |
| Daily transit rollover | Expire previous day's transit cache | Transit namespace |

### Manual Flush Command

```
CACHE_FLUSH ephemeris:*    // Flush all planetary position caches
CACHE_FLUSH chart:*        // Flush all chart feature caches
CACHE_FLUSH interp:*       // Flush all interpretation caches
CACHE_FLUSH transit:*      // Flush all transit caches
```

## Implementation Notes

- Use Redis `GET`/`SET` with `EX` (expiry) for Layer 1 and Layer 2
- Use PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` for Layer 3 (persistent storage)
- Populate Redis from PostgreSQL on cache miss (read-through pattern)
- Track `hit_count` on each cached interpretation to identify popular configurations
- Log cache miss ratios per namespace for monitoring
- Set a maximum cache size per namespace to prevent unbounded growth (LRU eviction for Redis)
